### Failure 1: deduxit's CI lost its runner while Kani ran

Three runs of `ci.yml` failed, not two: 43644944208 (2026-11-14 21:50),
43695073772 (08:33) and 43699904493 (09:34). Each ended with exit 143
and "The runner has received a shutdown signal"; the job's annotation
says "The hosted runner lost communication with the server. Anything …
that … starves it for CPU/Memory … can cause this error." The first
run's log was never uploaded (the API answers `BlobNotFound`). The
other two show the cause:
- the check `kani` ran `cargo kani --jobs 2` beside the other checks'
  builds (`test-core`, `features`, `core-wasm32`, `package`, `msrv`,
  the web module's build);
- harnesses took 145 to 1500 s each there (on this machine alone: 0.1
  to 582 s); the union of two zones and the sum of two zones were in
  flight together, each up to 8 GB, on a 16 GB runner;
- the runner died 5 to 10 minutes into the second pair: at 09:03 (run
  2, the doc tests running beside Kani) and at 10:16 (run 3, the web
  bindings' `cargo about` beside it).

The run that passed between them (43652664316) had the check's result
from the cache. The local check passed because this machine has the
memory for two harnesses and the builds together.

**What changed** (`wluzzkvq`):
- `modules/kani.nix`: the harnesses are `packages.kani-harnesses`, no
  longer `checks.kani`, so `nix flake check` and `ci.yml` skip them.
  They run `--jobs 1 --output-format terse`: one harness at a time
  (plain `cargo kani` without `--jobs` is sequential too; terse keeps
  the log to a summary per harness).
- `.github/workflows/kani.yml`: one job, `nix build .#kani-harnesses`,
  on `ubuntu-latest` with nothing else beside it, `timeout-minutes:
  240`. It runs weekly (Monday 07:17 UTC), by dispatch, and on pushes to
  `main` and pull requests that touch `core/src/linear/proofs/check/**`,
  `core/src/linear/proofs/mod.rs` (`Proof::reach`, which a harness
  calls), `modules/kani.nix` or the workflow. It uses the same pins,
  permissions and Cachix setup as `ci.yml`, so an unchanged derivation
  is fetched, and the weekly run catches what the paths miss (a lock
  bump, the core crate's other sources, `[workspace.metadata.kani]`,
  the Kani tag).
- CLAUDE.md (the command list, the verification table, the CI
  paragraph), `ci.md` (a Kani bullet with the failure), `flake.md`,
  `core-proofs.md`, `Cargo.toml`'s comment, the `update-deps` skill and
  `harnesses.rs`'s module doc name the package instead of the check.

**How Kani runs now**: not at a push of other code. On GitHub, when the
checker or the workflow changes, weekly, or by dispatch; locally `nix
build .#kani-harnesses` (32 minutes on 2026-11-15, under the machine
lock), and CLAUDE.md's verification table still asks for it when the
checker's integers change. The first run of `kani.yml` will be the push
of this commit (it touches the workflow), about an hour if Kani itself
comes from the cache.

### Failure 2: the client's Learn walk ran past 60 s

Run 43698511647 of `deduxit/deduxit.github.io` (the commit `flake.lock:
Update`, which moved the `deduxit` input from 8e2bbb18 to e7c5abd8)
failed five tests, each twice (with its retry):
- the axe spec's Learn walk in all four variants (light and dark,
  desktop and phone), not only the desktop's: "Test timeout of 60000ms
  exceeded", in axe's `analyze` or a click near the walk's end;
- `prover.spec.ts:837`, "an action asked for while a search runs
  waits": `Unprovable` did not show within the 5 s of its expectation.

The cause of the first: axe takes 1.5 to 4 s a state (Learn's Reference
4 s), the page's own work 0.1 to 1.3 s. The walk had twelve states,
about 33 s here on `--workers 1`; the longest walk that passed on the
runner (the phone's band and menus) takes 20.5 s here, so the runner
was 1.8 to 2.9 times slower. The new module is not slower: the prover
test's search took 0.94 to 1.15 s against the old lock's site and the
new one alike (three runs each, twice, interleaved).

**What changed** (`zkwnnqqs`), the split the client's rules prefer
(58b split `proving` and `menus` the same way; no time raised):
- `tests/states.ts`: `learning` (Learn's two places and lesson 2's
  parts, seven states) ends on the list of lessons; `attempting` (lessons
  7, 9 and 10, five states) goes on from there; `toLessons` opens Learn
  on that list.
- `tests/accessibility.spec.ts`: a walk "Learn's attempts" beside
  "Learn"; every state is still audited, in both schemes at both widths.
- `tests/targets.spec.ts`: `learning` then `attempting`, the walk
  unchanged.
- `.claude/rules/web.md`: a walk stays under 20 s here, with the
  figures and how to time one.

**Checked under a slower setting**: `CI=1` (60 s, no retry with
`--retries 0`) on one core with four workers (`taskset -c 13 …
playwright test tests/accessibility.spec.ts --workers 4`), against the
new site. The old spec failed its light Learn walks at 60 s, desktop
and phone; the split walks passed in 24 to 47 s, and the band and menus
walks in 34 to 57 s. Chromium's CPU throttling (a CDP
`Emulation.setCPUThrottlingRate` in the page fixture) was tried first:
at 6 it reproduced the failure once, but alone a throttled walk ran at
19 s against 17 s unthrottled, so it is no steady measure.

**The prover test is left as it is.** It passed in every earlier run,
passes here in 3.1 s, and passed 8 times of 8 on one core with four
